## Step 2 — Cause

**Named cause: the simulated LCP counts the whole first-load JavaScript, because locally that JavaScript has
finished and run before the first paint.** It is not a font swap, not the SplitText re-paint and not a
blocking stylesheet.

Evidence:

1. FCP and LCP are the same paint. In every run `observedFirstContentfulPaint == observedLargestContentfulPaint`
   (30–88 ms unthrottled). There is one `largestContentfulPaint::Candidate` in the trace, at the first contentful
   frame; no later candidate (so no font-swap re-record and no SplitText re-paint). Yet simulated FCP is 1356 ms
   and simulated LCP 2915 ms for that same paint.
2. The difference is the Lantern graph, not the page. Lantern builds the FCP graph from render-blocking requests
   only, but the LCP graph from *every* request except low-priority images that finished before the observed
   paint, plus the CPU tasks that started before it. In the /en trace all async first-load chunks are evaluated
   between DCL (24.6 ms) and the first contentful frame (45 ms), including react-dom (`244v…js`, 70 KiB,
   15 ms task ending at 45.6 ms). Summed per run: **160–162 KiB of script finished before the observed paint on
   every page** (/en, /en/contact, /en/work/geotrack alike). At 1.6 Mbps that is ≈ 0.8 s of transfer plus slow
   start and the 4× CPU cost of evaluating it, which is the 1.5 s gap between simulated FCP and LCP. The render
   delay of 2.4–2.7 s on every URL, text or image, is this same term.
3. Same page under real throttling: Lighthouse with `--throttling-method=devtools` on /en (3 runs) gives
   FCP 1407/1356/1356 and **LCP 1407/1356/1356** (= FCP, perf 98): on a throttled connection the browser paints
   the server-rendered headline long before the async chunks arrive.
4. Fonts are not the gate: with every `*.woff2` blocked (`--blocked-url-patterns`), the observed first paint is
   still after DCL and simulated LCP is still 2463–2557 (FCP 1209).
5. The bimodality noted in CLAUDE.md (≈2.3–2.4 s or ≈2.9–3.1 s for the same build) is Lantern deciding, from
   unthrottled task timing, whether some chunk's CPU work started before or after the cutoff; the page is the same.

Case pages add the cover image to the same graph: geotrack's 91 KiB cover (load delay 149 + load time 271 in the
breakdown) is why geotrack is 3.0–3.6 s against 2.9 s on text pages; karaoke-sync's 26 KiB poster costs little.

What follows for fixes: the only page-side levers on this metric are (a) fewer bytes/requests in the pre-paint
set (CSS round trip, first-load JS, the cover image) and (b) none of them can remove the ~160 KiB framework
runtime (react-dom 70 KiB, Next app router 46 KiB, next-intl client 16 KiB) without restructuring the app.

Attempt 1: FCP did not move and the document grew from 11.8 to 25.7 KiB (/en) and to 44.5 KiB (/en/work): the
stylesheet is inlined into the HTML *and* its payload is carried in the RSC data, and one stylesheet request
remains. A bigger document is a slower first byte-to-paint on 1.6 Mbps; /en/work's observed LCP moved to 335 ms
(list rows parsed later), which pulled more of the page into its LCP graph. Reverted.

Attempt 2: as the cause predicts, the fonts are already in the LCP graph (they finish before the observed paint),
so starting Satoshi earlier helps FCP (−300 ms) but not LCP. Side effects worth recording for a later decision:
CLS 0.012/0.015 → 0.000 on every URL (the residual shift is the Satoshi swap on the hero/case meta lines; it also
shows with all JS blocked, see below). Reverted under the keep rule (LCP did not improve); it conflicts with the
existing decision in `lib/fonts.ts` that only the LCP font is preloaded, so it is an owner call, not part of this task.

Stop: two consecutive attempts with no LCP gain (Step 3 stop rule). Remaining gap, with evidence:

- Floor experiment (no code change): /en with every `/_next/static/chunks/*.js` blocked → LCP **1952** ×3,
  FCP 1352, perf 99. So ≈ 960 ms of the 2915 ms median is first-load JavaScript counted by Lantern, ≈ 600 ms is the
  three fonts plus CSS, the rest is TTFB and the HTML.
- With every `*.woff2` blocked: LCP 2463–2557.
- Under devtools throttling the same build paints the hero headline at **1356–1407 ms** (LCP = FCP).
- Rejected without running (estimated gain below the 150–650 ms step between Lantern's two modes): re-encoding the
  geotrack cover at WebP q70 (93 → 78 KB, ≈ 75 ms; visible loss on a text-heavy screenshot); moving the app's
  own client components behind `lazy()` (≈ 20 KiB of non-framework code in the pre-paint set, ≤ 100 ms);
  removing the next-intl client runtime (16 KiB, ≈ 80 ms, needs `SiteFrame` and every client toggle reworked).
- Closing the gap on the simulated metric needs either a much smaller framework runtime (react-dom + Next
  router ≈ 116 KiB gz) or a different measurement (`throttlingMethod: "devtools"`), which changes every number
  and is noisier on shared CI runners. Both are owner decisions; neither is taken here.
